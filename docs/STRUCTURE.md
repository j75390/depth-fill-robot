# 프로젝트 구조 규칙

이 저장소는 **구조가 깔끔한 것**을 결과물만큼 중요하게 봅니다. 아래 규칙을 어기게 되면 먼저 이 문서를 고치고 이유를 판단 기록에 남깁니다.

## 폴더와 역할
```
configs/    실험 설정(toml). 숫자는 코드에 박지 않고 여기서 읽는다
src/depthfill/
  data/     데이터셋(합성, 공개 데이터 로더)
  holes/    구멍 만들기
  methods/  보완 방법(기준선, 모델). base.py의 Method 형태만 따른다
  eval/     지표와 평가 도구
scripts/    실행 진입점(학습, 평가, 환경 점검). 로직은 src에 두고 여기는 얇게
tests/      자동 시험(pytest)
docs/       계획, 판단 기록, 이 문서, 집 시작 안내
data/ results/ checkpoints/   내용은 저장소에 올리지 않는다(.gitkeep만)
```

## 코드 규칙
1. **한 파일은 한 가지 일만 한다.** 모델 정의, 학습, 평가를 한 파일에 섞지 않는다.
2. **torch는 `methods/unet.py`와 학습 스크립트에서만** 가져온다. 나머지(구멍, 지표, 평가 도구)는 torch 없이도 돌고 시험된다.
3. **정답 깊이는 방법에 넘기지 않는다.** `Method.fill`은 구멍 난 깊이만 받는다.
4. **같은 설정이면 같은 결과**: 무작위는 모두 시드로 고정한다(`np.random.default_rng([seed, ...])`).
5. 새 방법은 `methods/registry.py`에 한 줄만 더하면 평가 도구가 그대로 쓴다.
6. 숫자(해상도, 비율, 학습률)는 `configs/*.toml`에 두고, 바꿀 때 `docs/decision-log.md`에 이유를 적는다.
7. 노트북(.ipynb)은 쓰지 않는다. 실험은 스크립트와 설정 파일로 남겨 다시 실행할 수 있게 한다.

## 시험
- 모듈을 만들면 `tests/`에 시험을 함께 만든다. 시험은 **데이터를 내려받지 않고** 합성 장면만으로 돈다.
- 커밋 전에 `pytest`와 `ruff check .`가 통과해야 한다.

## 결과와 문서
- 결과 숫자는 **실제로 실행해서 확인한 것만** 적는다. 실행 설정(시드, 설정 파일)을 같이 남긴다.
- 모델이 기준선보다 나쁘면 그대로 쓰고 원인을 분석한다.
- 실제 로봇 데이터가 아니라 공개 센서 데이터와 시뮬레이션이라는 점을 README와 소개 자료에 분명히 쓴다.

## 작업 방식 (git)
- 이슈 하나당 브랜치 하나(`feature/<이슈번호>-이름`), PR로 병합한다. 급하면 PR 없이 main에 바로 올리지 말고 브랜치에서 작게 끝낸다.
- 커밋 메시지는 한국어로 "무엇을 왜"를 한 줄 요약하고 필요하면 본문에 적는다.
- 데이터, 체크포인트, 비밀값, 가상환경은 올리지 않는다(.gitignore).
